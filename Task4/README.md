## Задание 4. Проектирование продажи ОСАГО

### Реализация osago-aggregator

Функциональная обязанность этого сервиса — отправка заявок в страховые компании и дальнейший опрос решений по ним для передачи результатов в core-app.

**БД для osago-aggregator**

Для работы сервиса требуется хранилище БД (PostgreSQL).

* Для хранения заявок в страховые компании.
* Для хранения статусов заявок.
* Для хранения системных настроек и данных для флагов, задач, rate-limits и пр.

**API между osago-aggregator и core-app**

Сервис osago-aggregator предоставляет REST API:

* POST /v1/requests. Создает заявку. Возвращает идентификатор request_id заявки. 
* GET /v1/requests. Возвращает заявки со статусами с постраничным режимом.
* DELETE /v1/requests/{id}. Отменяет заявку.

**Сообщения по заявкам**

* OsagoRequestStatusChanged. Заявка изменила статус. CREATED, COMPLETED, CANCELED, PROCESSING, FAIL.

### Отказоустойчивость

**Rate Limiting**

* В osago-aggregator - на количество одновременных запросов к партерам. На одного партнера.
* В core-app — лимиты на создание новых заявок.

**Circuit Breaker**

* В osago-aggregator для каждого партнера после заданного количества отказов за период или при высокой задержке ответа на запросы.
* В core-app для платежного сервиса после заданного количества отказов за период. 

**Retries**

* В osago-aggregator выполняются попытки вызовов к API страховой компании при сетевых сбоях и 5xx-ошибках.
* В core-app выполняются попытки вызовов для идемпотентных запросов к osago-aggregator.

Выполняется 2 попытки повтора с нарастающим сдвигом (2с - 4с). 
Добавляется случайное смещение, чтобы при массовом сбое не устроить «шторма» запросов.

**Timeouts**

* Вызовы osago-aggregator к API страховой компании должны иметь ограничение по времени (2-5с).
* Вызовы core-app для платежного сервиса должны иметь ограничение по времени (2-15с).
